# 引擎优化方案（2026-09-25 核验）

## 结论与范围

基于当前仓库代码核验。已落地第一阶段的 EngineHost、System 集中注册、脚本热重载轮询优化，以及第二阶段的首批资源异步加载改造。性能收益是预期，不把估算当实测结果。

## 原建议核验

| 项目 | 核验结论 | 依据或修正 |
| --- | --- | --- |
| 窗口运行逻辑重复 | 属实，已处理 | 原 MainWindow/GameWindow 各自注册同组 System、驱动 Time/Engine/Input/SceneRouter、维护捕获光标及析构解绑。窗口现在调用 Core/EngineHost 与 Core/EngineSystems。 |
| Engine 构造依赖资源、音频、脚本清理 | 属实，已处理 | OnRemove observer 已迁到 Core/EngineObservers.cpp，由 Engine 构造时注册并由 world 持有；Engine.h 不再包含资源/音频服务实现头。 |
| 魔数分散 | 部分属实 | Time 已有 kUpdateFPS/kPhysicsFPS；ShadowRenderer 也有阴影图尺寸常量。只集中跨模块必须同步的配置，例如 C++ 与 shader 的光源上限。 |
| 脚本每实体每帧 stat | 属实，已处理 | 原 ScriptSystem::update 每帧检查 filePath。编辑器现按 0.5 秒、每唯一路径检查一次；导出游戏关闭。内置脚本编辑器保存仍主动 reloadScript。 |
| 资源首访同步加载 | 属实，已改造首批路径 | OBJ 解析和图片解码已移至工作线程；GL 上传仍在渲染线程限额执行。需测量 IO、解码与上传各自耗时。 |
| 所有渲染都无实例化 | 不准确 | 场景 mesh 仍逐实体 draw；粒子已经使用 glDrawArraysInstanced。场景批处理方案不应重复改造粒子。 |
| Gizmo 旋转/缩放待实现 | 不准确 | MainWindow 有 W/E/R 模式切换，GizmoRenderer 有旋转与缩放拖拽及结果提交。后续工作是精度、轴约束和 UI 易用性验证。 |
| 动画编辑器 UI 待实现 | 不准确 | EditorPanel 已有动画选择、时间滑块、缓动参数及打关键帧。可以扩展独立多轨时间轴，但不应记作空白功能。 |
| SSAO 可直接采现有深度 | 不准确 | PostProcessor 的 HDR FBO 使用 GL_DEPTH_COMPONENT24 renderbuffer，不能直接采样；需改深度纹理或加入 G-buffer/位置重建，并增加 SSAO 与 blur pass。 |
| Sphere/Capsule 碰撞待实现 | 属实，已处理 | SphereColliderComponent 与 CapsuleColliderComponent 已贯通 Jolt、Inspector、场景反射序列化、Lua 和导航烘焙。 |
| IBL、glTF、ECS UI、2D TileMap | 当前未见实现 | PBR shader 仍以直接光照为主；这些属于新功能，优先级应受目标项目需求约束。 |

## 实施顺序与验收

### 阶段一：运行时基础（本次完成）

1. EngineHost 管理 Engine、QTimer、时间步进、帧末切场景、输入路由、Play/Edit 回调绑定和析构解绑。窗口保留界面、场景路径与加载策略。
2. registerDefaultSystems 是唯一默认 System 注册点，返回编辑器 Stop 所需的物理、脚本和音频句柄。
3. 游戏禁用脚本 mtime 轮询；编辑器按 0.5 秒扫描一次唯一路径，保存时主动重载。
4. 已验证：编辑器/游戏 Debug 构建、脚本热重载与宿主析构集成测试。仍需在可交互图形环境冒烟 Play→Stop→Play、切关、直接关闭窗口，并用性能工具核对稳定运行时 stat 次数。后续修改 System 仅改注册点与构建清单。

### 阶段二：资源和场景加载

已实现 OBJ 解析和图片解码的后台任务，渲染线程每帧最多处理两个完成结果并在约 3ms 后停止继续上传；加载场景后预热网格、当前精灵帧和材质贴图，并取消前一场景的待处理任务。句柄代数校验可丢弃卸载或复用后的过期结果，失败会写引擎日志。材质贴图路径现可随场景存盘，运行时句柄仍按引用计数管理。接下来建立有代表性的 200/1000 实体场景，记录 p50/p95 帧时间、场景切换耗时、IO/解码/GL 上传分段耗时；根据实测结果调整队列、上传预算及预取范围。3ms 是处理间隔目标，单次 GL 上传仍可能超过预算，不能视为硬实时保证。

### 阶段三：渲染和物理

首批已落地共享渲染列表：每帧收集一次可绘制网格，按真实网格局部 AABB 与完整世界矩阵计算世界包围盒；主视图、相机预览、方向/聚光阴影和点光六面分别做视锥裁剪。主视图复用连续相同的纹理绑定。需用实际场景记录 draw call、纹理绑定、CPU 编排耗时及 p95 帧时间，确认净收益。后续对不透明 mesh 才考虑按材质/纹理排序；透明对象需要保留正确深度顺序。仅在重复静态 mesh 足够多、且测量证明有收益时加实例化。球/胶囊碰撞体已接入 Inspector、反射序列化、Lua 构建 API、Jolt 形状与导航烘焙，并有曲面射线及存盘回归测试。物理容器改 unordered_map 前先做实体规模基准。

### 阶段四：画面与产品能力

IBL 先做环境贴图、irradiance、prefilter 与 BRDF LUT，再对比直接光照下的材质观感。SSAO 先解决可采样深度、法线和重建，再实现遮蔽及降噪。CSM 在方向光远景阴影确有质量问题时做。场景树名称搜索已完成；编辑器下一步补多选与资源预览，已有 Gizmo 和动画面板优先打磨。ECS UI、glTF 骨骼、2D TileMap、跨平台导出和插件系统分别立项，先定义最小可玩用例与测试资产，再安排开发。渲染后端抽象放在需要第二后端时实施，避免为假定的接口重写现有 GL 管线。

## 关键约束

- 资源异步化消除的是主线程 IO/解码阻塞；GPU 上传仍需预算控制，不能保证零卡顿。
- 只用局部 Transform 做剔除会误判父子层级实体；需使用世界矩阵和真实 mesh bounds。
- 全局 EngineConfig 不应收纳所有数字。尺寸、容差等由所属模块管理；跨 shader/C++ 的值用单一生成源或构建校验。
- 每阶段先保留可回退的行为路径，并以测量和场景回归决定是否进入下一阶段。
