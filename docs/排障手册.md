# 排障手册（Troubleshooting）

> 实战踩坑记录：每条按 **症状 → 根因 → 修复 → 快速定位** 组织。
> 更早的坑 1~14（HFSM2 拷贝、Flecs get 崩溃、WIN32 无控制台等）见 `../模块文档.md` 第八节。
> 本文件记录「多场景游戏 + 导出」实战期间（坑 15 起）抓出的问题。

## 坑 15：手写场景 JSON 全部字段变 0（"场景里只有一个盒子"）

**症状**：加载场景后所有实体挤在原点重叠（看着像只有一个盒子）、玩家控制不了、相机位置错乱。

**根因**：flecs JSON 反序列化要求它自己的嵌套格式，手写的两种直觉格式都解析失败且**静默跳过**（字段全部保持默认值 0）：

```json
手写（都错）：                     flecs 实际要的：
"position": [0, 3, 0]              "position": [{ "x": [0], "y": [3], "z": [0] }]
"position": {"x":0, "y":3, "z":0}
```

**修复**：场景文件**永远用引擎自己生成**（编辑器 💾 保存 / `SceneSerializer::save` / test_gameplay 程序化建场景后 save），绝不手写。

**快速定位**：控制台版程序加载场景后打印实体 position——若明明配了非零值却读出 (0,0,0)，且 stderr 有 `flecs: expected '['` / `unsupported conversion`，就是格式问题。

## 坑 16：编辑器点 ▶ 运行后 WASD 动的是相机不是角色

**症状**：Play 模式按 W，视角飞走，游戏角色不动；看到的也不是游戏相机的画面。

**根因**：编辑器相机（isEditor=true, active=true）在 Play 时仍然激活——CameraSystem 继续用 WASD 驱动它，RenderWidget 也优先用它渲染。

**修复**（MainWindow onEnterPlay）：场景里有游戏相机时，把编辑器相机 `active=false` 让位；退出 Play 恢复。CameraSystem 只驱动"激活的编辑器相机"（`isEditor && active`）。

**快速定位**：按 W 时若右键环视的视角在动 → 编辑器相机还在吃输入。

## 坑 17：站一会儿之后推不动 / set_velocity 失效

**症状**：角色落地静止约半秒后，WASD/冲量全部失效，像被冻住。

**根因**：Jolt 刚体静止后自动**睡眠**（省性能），而 `SetLinearVelocity` / 部分操作**不会唤醒**睡眠刚体。

**修复**：`physicsSetVelocity` / `physicsApplyImpulse` 先 `ActivateBody` 再操作。

**通用规律**：所有物理引擎（Jolt/PhysX/Bullet）都有睡眠机制——**任何"从外部改睡眠刚体"的操作都要先唤醒**。

## 坑 18：传送门第一次切错场景，第二次才对

**症状**：第一次走进传送门"被传回原点"（其实是重载了当前场景），第二次才切到正确场景。

**根因**：编辑器 📂 加载场景时没有登记"当前场景名"（SceneRouter::current 为空串）→ 脚本 `get_scene()` 返回 ""，`string.find("", "level1")` 为 nil → 走错分支切到自己。第一次切换顺带把 current 设对了，所以第二次正常。

**修复**：所有加载场景的入口（编辑器加载按钮 / GameWindow / Play 帧末切换 / 退 Play 恢复备份）都必须同步 `SceneRouter::setCurrent`。

**通用规律**："当前 XX"这类全局状态，**每个改变它的入口都要同步更新**，漏一个入口就出"第一次错第二次对"的诡异现象。

## 坑 19：落地检测射线的起点两难（跳跃判定失效）

**症状**：空格跳不了（落地检测永远 false）；或射线永远命中（打中自己）。

**根因**：射线起点放哪都不对——放自己碰撞体内部会命中自己（Jolt 对 convex 内部起点返回 fraction=0 命中）；挪出自己盒子又容易扎进地面内部（从地面形状内部发射 → 不命中地面）。

**修复**：不调坐标，用**过滤器**——`physicsRaycast` 加 `ignoreEntity` 参数（`JPH::IgnoreSingleBodyFilter`），Lua `raycast` 自动忽略发射者。射线放心从自身中心发。

**通用规律**：Godot `intersect_ray` 的 exclude 同款语义——"射线不打自己"要靠 BodyFilter，不靠起点微调。

## 坑 20：按空格弹开工具栏下拉框（游戏按键被 UI 吃掉）

**症状**：Play 模式按空格，编码下拉框弹开；W/S 触发控件首字母匹配。

**根因**：三层叠加——

1. QComboBox 默认接受键盘焦点，空格是它的激活键；
2. app 级 eventFilter `return false` 只是"偷看"，不阻止事件继续传给焦点控件；
3. `QOpenGLWidget` 默认 `NoFocus`，对它调 `setFocus()` 是**空操作**（焦点根本移不过去）。

**修复**：① 工具栏输入控件 `setFocusPolicy(Qt::NoFocus)`；② 视口 `setFocusPolicy(Qt::StrongFocus)` 后进 Play `setFocus()`；③ 根治：Play 模式下 KeyPress/KeyRelease 在 Input 记录后 `return true` 拦截，不再传播给任何 UI。

**通用规律**：拿 Qt 做游戏引擎，**运行模式必须明确切断"按键→UI 控件"的传播**，否则游戏按键和控件快捷键必然打架。

## 坑 21：读档/重生瞬移失败（set_position 被拉回原地）

**症状**：读档后角色纹丝不动；掉落重生无效——但存档文件内容是对的。

**根因**：带 Dynamic 刚体的实体，位置的"真身"在物理引擎里。`set_position` 只写 Transform，下一帧 PhysicsSystem 用刚体位置回写 Transform → 改动被覆盖。

**修复**：`set_position` / `set_node_position` 双通道——写 Transform（渲染立即生效）+ `physicsSetPosition`（Jolt `SetPosition` + Activate，物理真身一起搬）。

**通用规律**：**谁拥有数据的"真身"，写操作就必须写到谁那里**。物理接管后 Transform 只是每帧的抄写员：读它没问题，写它无效。

## 坑 22：跳跃"完全失效"——方块默认重达一吨（本轮最深的坑）

**症状**：`apply_impulse(0,6,0)` 毫无反应；但移动、重力、碰撞全部正常。

**根因**：建 Jolt 物理体时**没把 `RigidbodyComponent.mass` 传过去**。Jolt 收不到质量就按"体积 × 默认密度 1000kg/m³"自动计算 → 1×1×1 方块 = **1000 公斤**。冲量 6 只产生 Δv = 6/1000 = 0.006 m/s——跳跃"生效着"，只是慢到看不见。

**为什么其它全正常（藏得深的原因）**：

- 重力加速度与质量无关 → 掉落正常；
- `set_velocity` 直接设速度、绕过质量 → 移动正常；
- 只有"力/冲量"类操作被千倍质量吞掉。

**修复**：`BodyCreationSettings.mOverrideMassProperties = CalculateInertia` + `mMassPropertiesOverride.mMass = rb.mass`。

**快速定位**（数值反推法）：impulse 后读 `get_velocity`，用 Δv = J/m 反推实际质量。本例 vy=0.01 → m ≈ 6/0.006 = 1000kg，一个数字破案。

**通用规律**：**组件里配置字段存在 ≠ 配置生效**。加新字段时检查清单必须多一条："消费端（物理/渲染/序列化）真的读了这个字段吗？"这类"断线"bug 无报错、大部分功能正常，最难发现。

## 坑 23：集成 miniaudio 后 flecs.h 满屏语法错（min/max 宏污染）

**症状**：加入 `#include "miniaudio.h"` 后，编译报 `flecs.h` 里 `std::numeric_limits<U>::min()` 一片语法错（C2589 “(”非法标记等），错误位置在完全无关的第三方头。

**根因**：miniaudio 实现会拉进 `Windows.h`，它定义了 `min`/`max` 两个宏，把后续所有 `::min()` / `::max()` 调用展开破坏（Windows 头最出名的坑）。

**修复**：include miniaudio.h **之前** `#define NOMINMAX`（外加 `WIN32_LEAN_AND_MEAN` 减少宏污染面）。

**通用规律**：任何会间接拉进 `Windows.h` 的库（miniaudio/部分音视频库），在包含前必须 `NOMINMAX`。报错出现在无关的 STL/第三方头里 = 十有八九是宏污染。

## 坑 24：QOpenGLWidget 里 FBO/setFocus 的两个"非 0"陷阱

**症状**：① 后处理全屏渲染后画面全黑或残缺；② `setFocus()` 明明调了却不生效。

**根因**：

1. **屏幕不是 FBO 0**：`QOpenGLWidget` 的默认渲染目标是 `defaultFramebufferObject()`（一个非 0 的 FBO），不是裸的 `0`。后处理结束想"画回屏幕"时 `glBindFramebuffer(GL_FRAMEBUFFER, 0)` 会绑到错误目标。
2. **焦点策略默认 NoFocus**：`QOpenGLWidget` 默认 `focusPolicy=NoFocus`，对它 `setFocus()` 是空操作（坑 20 同源）。

**修复**：① 上屏用 `defaultFramebufferObject()` 而非 0；② 视口 `setFocusPolicy(Qt::StrongFocus)` 后 setFocus 才有效。

**通用规律**：拿 QOpenGLWidget 做多 Pass 渲染，"默认帧缓冲"和"能否接收键盘"这两件事都不是裸 GL 直觉里的样子——都要走 Qt 的接口拿。

## 坑 25：Release 独立运行报"无法定位程序输入点"（MinGW/MSVC 双 Qt 冲突）

**症状**：Debug 用 IDE 能跑，手动编的 Release 双击报 `无法定位程序输入点 ?isIndexHidden@QTreeView@@... 于动态链接库 my_demo.exe`。注意是"定位入口点"（entry point）不是"找不到 DLL"。

**根因**：系统 PATH 里装了**两个同版本 Qt**——`D:\QT\5.14.2\mingw73_64\bin`（MinGW/GCC 编译）和 `msvc2017_64\bin`（MSVC 编译），且 MinGW 排在前面。exe 是 MSVC 编的，导入 MSVC 命名的符号（`?isIndexHidden@QTreeView@@...`）；MinGW 版 Qt5Widgets.dll 导出的是 GCC 命名（`_ZN9QTreeView...`）——版本号相同但**编译器不同=符号名不同**。

- Debug 能跑：IDE 通过 `VS_DEBUGGER_ENVIRONMENT` 把 MSVC 的 bin 塞到 PATH 最前，避开了 MinGW。
- "找不到 DLL" vs "定位入口点"：前者是 DLL 缺失，后者是 **DLL 找到了但版本/编译器不对**——后者专指版本/ABI 不匹配。

**windeployqt 的两个坑（元凶）**：

1. **它顺 PATH 抓 DLL**——运行 windeployqt 时 MinGW bin 在 PATH 最前，于是它把 **MinGW 版** Qt DLL 部署到了 exe 旁边（用文件大小或"是否含 libstdc++ 字符串"可验证：MinGW 版更大且含 libstdc++）。
2. **它按版本号判重**——重跑时看版本号相同(5.14.2.0)就 "up to date" 跳过，**不会**用 MSVC 版覆盖错误的 MinGW 版。
3. 还漏部署了 `Qt5OpenGL.dll`（exe 链接 Qt5::OpenGL）。

**正确修复**：**直接拷贝** MSVC 版 DLL 覆盖 exe 旁边的所有 Qt DLL（`Copy-Item -Force`，绕开 windeployqt 的判重），补上 `Qt5OpenGL.dll`，并把 `platforms\qwindows.dll` 平台插件也换成 MSVC 版（MinGW 版插件同样会加载失败）。验证：部署的 Qt5Widgets.dll 大小从 8623912(MinGW) 变成 5596280(MSVC)，exe 独立运行正常。

**通用规律**：装了多个编译器版本的 Qt（MinGW+MSVC 混装）时，`windeployqt` **不可靠**——它靠 PATH 找 DLL、靠版本号判重，两者都会让它部署/保留错误的编译器版本。可靠做法：部署时把 PATH 清成只剩目标 Qt 的 bin，或干脆直接 Copy-Item 覆盖。判断某 DLL 是 MinGW 还是 MSVC：看是否含 `libstdc++`/`libgcc` 导入（MinGW）或 `VCRUNTIME`（MSVC）。

**导出按钮已彻底避开此坑（2026-07 起）**：「📦 导出游戏」不再调 windeployqt，改为直接从 `QLibraryInfo::BinariesPath`（= 编辑器编译期链接的那个 Qt bin，天然与 exe 编译器一致的 MSVC 版）拷核心 DLL + Qt5OpenGL + platforms/qwindows.dll。从源头保证部署的编译器版本正确，导出的游戏发给别人不会再"无法定位程序输入点"。手动编的 Release 仍需自己按上面的方式部署。

## 坑 26：第一次 Play 正常，第二次 Play 视角/状态不正常（脚本环境跨会话残留）

**症状**：第一次 ▶ 运行一切正常；退出再次 ▶ 运行：鼠标不锁定（转视角转到屏幕边就卡住）、第一人称能看到自己的方块、出生朝向不对。

**根因**：脚本环境跨 Play 会话复用——`wasReady` 标记一旦置 true 就永久保留，第二次 Play 时 `ready()` **不再执行**。而初始化全在 ready 里：`set_mouse_mode("captured")`（退 Play 时被强制 visible）、`set_visible(false)`、`local yaw/pitch` 归零。全部缺失 → 视角"不正常"。

**修复**：`ScriptSystem::resetAllScripts()`——退出 Play 时释放全部实体的 Lua 环境（luaL_unref + 清 envRefs/wasReady 表），下次 Play 时 update 发现无环境 → 自动重建 + 重跑 ready()，local 变量随新环境归零。字节码缓存保留（源码没变无需重编译）。

**通用规律（Godot 语义）**：**"停止运行 = 销毁全部运行时状态"**。任何跨 Play 会话残留的状态（脚本环境/单例草稿/输入模式/动画进度）都是"第二次运行不正常"类 bug 的温床——退出 Play 的清理清单每加一种新状态就要多一项（本项目现有：Transform 快照恢复、动画停止、光标重置、音频停止、脚本环境重置）。

## 排障方法论（比单个坑更重要）

本轮全部问题都靠同一套打法破案，沉淀如下：

### 1. 可视化诊断（WIN32 无控制台的现实）

GUI 程序里 `printf`/Lua `print` 全部不可见。诊断输出必须走用户看得见的通道：

- **状态栏**：`statusBar()->showMessage(...)` —— 验证 C++ 层事件；
- **实体颜色**：脚本里 `add_material(me, r, g, b)` 当调试灯 —— 验证 Lua 层分支；
- **位置编码**：探针脚本把结果写进自己的 y 坐标（111/222/333 分别代表不同状态）。

### 2. 分层探针（test_gameplay.exe，控制台版最小复现）

不开 GUI，程序化建场景 + 模拟按键 + 逐层断言：

```
[1] 物理体创建了吗（bodyId != 0）
[2] 重力生效了吗（y 在下降）——物理层独立验证
[3] 脚本推得动吗（按 W 后 z 变化）——输入→脚本→物理全链路
[4] 跳得起来吗（空格后 y 上升）
```

哪层 FAIL 病灶就在哪层与上一层之间。二分不猜。

### 3. 数值反推

拿到异常数值别只当"不正常"，**用公式反推出隐藏参数**：
vy=0.01 + 冲量 6 → 质量 1000kg → 直接联想到 Jolt 默认密度。数字会招供。

## 坑 27：脚本在 world.each 遍历中做结构变更 → flecs 表锁 assert 崩溃

**症状**：脚本里调 `connect_to`（给目标实体首次加 SignalComponent）时直接崩：
`assert(!src_table->_->lock): a "move" operation failed because the table is locked (LOCKED_STORAGE)`。spawn/destruct/首次 add 组件同理。

**根因**：ScriptSystem 原来在 `world.each` 遍历中直接执行 Lua——flecs 迭代期间表被锁，脚本做任何"结构变更"（加/删组件导致实体换表）都撞锁。集成测试第一次跑 P1 回归用例就实锤了。

**修复**：ScriptSystem::update 改**两阶段执行**（Godot 同款）：阶段一 `world.each` 只收集实体 ID；阶段二遍历 ID 列表执行脚本——此时不在 flecs 迭代中，结构变更全安全。注意阶段二要逐实体复查 `is_alive()` + 重取组件指针（脚本可能删了后续实体/组件，旧指针可能因换表失效）。

**教训**：在 ECS 遍历回调里调用"可能改动实体结构"的外部代码（脚本/事件回调）是通用雷区。要么两阶段，要么 defer_begin/defer_end。

## 坑 28（审查修复批）：资源登记了，回收路径没闭环

一次外部代码审查抓出 4 个同根因问题，全是"**创建/登记时正常，某条退出路径没回收**"：

| 问题 | 泄漏点 | 修复 |
|------|--------|------|
| 信号回调（P1） | 实体死亡时 signalMap 的 Lua ref 从不 unref；listensTo 反向索引是死代码 | SignalComponent OnRemove observer → cleanupEntitySignals 双向清理 |
| 异步回调（P2） | worker 编译/运行失败路径直接 return，cbRef 永久泄漏 | 失败也入队（ok 标志），主线程统一 unref |
| 一次性音效（P4a） | play_sound 塞进 map"说好 update 清"但清理代码不存在 | oneShots 独立列表，update 扫 at_end → uninit+erase |
| 死亡实体音源（P4b） | AudioComponent 无 OnRemove observer，循环音永远播 | observer → audioReleaseHandle |

**检查口诀**：新增任何"句柄/ref/handle"类资源时，三条路径都要闭环——
① 正常释放路径 ② 失败/异常路径 ③ 宿主实体死亡路径。
项目正确范本：Mesh/Sprite/Audio/Signal 的 OnRemove observer（Engine.h 统一注册）。

## 坑 29：脚本 update(dt) 偶发收到 nil → "attempt to perform arithmetic on a nil value (local 'dt')"

**症状**：游戏跑着跑着输出面板刷屏上述错误，且**偶发**（不是每帧）——对 dt 做减法的脚本（如冷却计时 `cd = cd - dt`）才炸，只读 dt 的脚本安然无恙。

**根因**：`callLifecycle` 曾用 `dt > 0` 判断"要不要给 Lua 传参"（想区分 ready 无参/update 带参）。但帧间隔恰好为 **0ms** 时（QElapsedTimer 毫秒精度，两帧挤同一毫秒），update 被调用却不传参 → 脚本端 dt=nil。

**修复**：加显式 `bool hasDt` 参数声明传参意图，dt=0 也如实传数字 0。回归测试 `Update_ZeroDt_StillReceivesNumber` 固化。

**教训**：**用业务值当控制标志（魔法值语义复用）是定时炸弹**——"dt>0 才传参"在 99.9% 的帧成立，剩下 0.1% 就是刷屏的偶发 bug。控制语义要用独立参数显式表达。
