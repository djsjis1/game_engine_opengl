# 03 · 上下文传递模式 —— `__active_ctx`

> 这是本项目 Lua↔C++ 架构中最精妙的设计。
> 理解了它，你就理解了整个脚本系统的核心。

---

## 3.1 核心问题

### 场景

```
进程中有 100 个脚本实体，共享 1 个 Lua VM。

实体 #42 的脚本执行 self:set_position(1, 2, 3) 时，
C 函数 api_setPosition 怎么知道要修改实体 #42 的 Transform，
而不是实体 #99 的？
```

### 三种方案对比

| 方案 | 写法 | 优点 | 缺点 |
|------|------|------|------|
| **A: 传 entity_id** | `set_position(42, 1, 2, 3)` | 直观 | 脚本写起来丑，每调用都要传 ID |
| **B: 闭包** | 每个实体创建独立闭包 | 自动绑定 | 每个实体分配 15 个闭包，100 实体 = 1500 个闭包 |
| **C: 注册表传上下文** ✅ | `self:set_position(1, 2, 3)` | 脚本简洁、零分配 | 需要理解注册表机制 |

**本项目选了方案 C**。

---

## 3.2 核心思路

```
ScriptSystem::update()                         Lua VM
─────────────────────                         ──────

遍历到实体 #42:
                                              ┌─────────────────┐
  ① 构造上下文                                │  注册表          │
     LuaCtx ctx = {                           │                 │
       .tf = &tf_of_entity_42,    ──────────→ │ ["__active_ctx"]│
       .w  = &world,              写入注册表   │   = &ctx        │
       .id = 42                              │        ↓         │
     };                                      │  指向 C++ 栈上的 │
                                              │  LuaCtx 结构体   │
  ② 调用 Lua: update(dt)                     │                 │
     ↓                                       │                 │
     Lua 脚本执行:                             │                 │
       self:set_position(1, 2, 3)            │                 │
         ↓                                   │                 │
         api_setPosition 被调用:               │                 │
           getCtx(L) ─────────── 读注册表 ──→ │ ["__active_ctx"] │
             → 拿到 &tf_of_entity_42         │                 │
             → tf->position = (1, 2, 3)      └─────────────────┘
                                               ↑
  ③ 实体 #42 的 Transform 已被修改             │
     (零拷贝！直接写了 C++ 内存)                │
```

## 3.3 实现细节

### 步骤 1：定义上下文结构体

```c
// LuaCtx —— 告诉 API 函数"当前是哪个实体在执行"
struct LuaCtx {
    TransformComponent *tf;  // 当前实体的 Transform（直接写 C++ 内存！）
    flecs::world       *w;   // ECS 世界指针（查询/创建其他实体用）
    flecs::entity_t     id;  // 当前实体的 ID
};
```

**为什么存指针而不是拷贝数据？**

```
❌ 拷贝方案:              ✅ 指针方案（本项目）:
                                    
C++ 端有一份 Transform    C++ 端有一份 Transform
   ↓                         ↑
LuaCtx 拷贝一份             LuaCtx 存指针 → 指向同一块内存
   ↓                         ↑
Lua 修改 LuaCtx 里的副本    Lua 修改 → 直接改了 C++ 的内存！
   ↓                     
需要同步回去 ← 麻烦 + 可能丢数据
```

**这就是"零拷贝"的含义**：`set_position` 改的就是 C++ 里 `TransformComponent` 的那块内存，不需要序列化/反序列化。

### 步骤 2：写入注册表

```c
void ScriptSystem::update(flecs::world &world, float dt) {
    world.each([&](flecs::entity e, TransformComponent &tf, ScriptComponent &sc) {
        
        // ① 把当前实体的上下文存入注册表
        LuaCtx ctx = { &tf, &world, e.raw_id() };
        lua_pushstring(L, "__active_ctx");     // key
        lua_pushlightuserdata(L, &ctx);        // value（裸指针）
        lua_settable(L, LUA_REGISTRYINDEX);    // registry["__active_ctx"] = &ctx
        //                                              ↑
        //  ctx 在 C++ 栈上！只在本次 update() 调用期间有效
        
        // ② 调用 Lua
        callLifecycle(L, envRef, "update", dt);
        
        // ③ ctx 随 update() 返回自然销毁（不需要清理注册表）
    });
}
```

**关键安全点**：

- `ctx` 在 C++ 栈上（不是堆分配），只在本次 lambda 调用期间有效
- 注册表存的是 `lightuserdata`（裸指针），**不管理生命周期**
- 必须在 `ctx` 失效前完成 Lua 调用，不能异步

### 步骤 3：读取注册表

```c
static LuaCtx *getCtx(lua_State *L) {
    lua_pushstring(L, "__active_ctx");         // ① 压入 key
    lua_gettable(L, LUA_REGISTRYINDEX);        // ② 取出 registry["__active_ctx"]
    auto *c = (LuaCtx *)lua_touserdata(L, -1); // ③ 转为 LuaCtx*
    lua_pop(L, 1);                             // ④ 清理栈
    return c;
}
```

### 步骤 4：API 函数使用

```c
static int api_getPosition(lua_State *L) {
    auto *c = getCtx(L);              // 拿到当前实体的上下文
    lua_pushnumber(L, c->tf->position.x);  // 读 Transform 内存
    lua_pushnumber(L, c->tf->position.y);
    lua_pushnumber(L, c->tf->position.z);
    return 3;
}

static int api_setPosition(lua_State *L) {
    auto *c = getCtx(L);
    c->tf->position.x = (float)luaL_checknumber(L, 1);  // 直接写！
    c->tf->position.y = (float)luaL_checknumber(L, 2);
    c->tf->position.z = (float)luaL_checknumber(L, 3);
    return 0;
}
```

## 3.4 `lightuserdata` vs `userdata`

这是 Lua C API 中常见的混淆点：

| | lightuserdata | userdata |
|---|---|---|
| **本质** | `void*` 裸指针 | Lua 分配的内存块 |
| **生命周期** | C 端管理 | Lua GC 管理 |
| **元表** | 不支持 | 支持（可实现 `__index`、`__gc`） |
| **大小** | 1 个指针 | 可任意大小 |
| **适用场景** | 引用 C 端已有对象 | 在 Lua 端创建新对象 |
| **本项目用途** | 传递 `LuaCtx*` | — |

```c
// lightuserdata: 存一个裸指针
LuaCtx ctx = {...};
lua_pushlightuserdata(L, &ctx);
// Lua 端看到这个值是 userdata 类型，但无法对它做任何操作
// 只能传回给 C 函数使用

// userdata: Lua 分配内存，管理生命周期
MyStruct *p = (MyStruct *)lua_newuserdata(L, sizeof(MyStruct));
// Lua GC 会在没有引用时自动释放这块内存
// 可以设 __gc 元方法做清理
```

## 3.5 为什么不把 LuaCtx 直接放全局变量？

```c
// ❌ 方案：全局变量
static LuaCtx *g_currentCtx = nullptr;

void bad_update(...) {
    g_currentCtx = &ctx_of_entity_42;
    callLua();  // 如果 callLua 内部又触发了另一个实体的 update？
    // → g_currentCtx 被覆盖，实体 42 的回调会读到错误的数据！
}
```

**注册表方案的优势**：虽然本项目是单线程、同步调用，用全局变量也行，但注册表方案更规范：

- 未来支持协程时，每个协程可以有独立的上下文
- 不需要手动管理覆盖/恢复

## 3.6 总结

```
┌─────────────────────────────────────────────────────┐
│            上下文传递模式 三步走                       │
│                                                     │
│  ① 调用 Lua 前: 把 LuaCtx {tf*, world*, id} 写入    │
│                 注册表 registry["__active_ctx"]      │
│                                                     │
│  ② Lua 执行中: API 函数通过 getCtx(L) 取出上下文     │
│                直接读写 C++ 内存（零拷贝）            │
│                                                     │
│  ③ 调用结束后: ctx 在 C++ 栈上自然销毁               │
│                 （lightuserdata 不管理生命周期）      │
└─────────────────────────────────────────────────────┘
```
