# AI 工作流规范

## 核心原则

AI 禁止直接输出大量代码。必须先分析、设计、规划，再实现。

任何需求必须按照以下七步流程执行，不得跳过任意步骤。

---

# Step 1：需求分析

理解用户真实意图，而非字面需求。

输出格式：

```markdown
## 需求分析

1. 用户意图：[一句话描述核心目标]
2. 功能边界：[做什么 / 不做什么]
3. 非功能需求：[性能、安全、兼容性等]
4. 隐含约束：[现有架构限制、技术栈限制等]
```

若需求不明确，必须先向用户确认，禁止猜测后直接编码。

---

# Step 2：影响范围分析

分析本次变更将触及的所有模块和文件。

输出格式：

```markdown
## 影响范围

### 新增文件
- path/to/new_file.h
- path/to/new_file.cpp

### 修改文件
- path/to/existing_file.h — [修改原因]
- path/to/existing_file.cpp — [修改原因]

### 删除文件
- path/to/deprecated_file.h — [删除原因]

### 不修改但受影响
- path/to/caller.cpp — [间接影响说明]
```

---

# Step 3：设计方案

至少提供两个方案并给出推荐。

输出格式：

```markdown
## 设计方案

### 方案 A：[名称]
- 思路：[简述]
- 优点：[列出]
- 缺点：[列出]

### 方案 B：[名称]
- 思路：[简述]
- 优点：[列出]
- 缺点：[列出]

### 推荐：方案 X
- 选择原因：[说明]
```

涉及架构级变更必须画出 Mermaid 时序图或类图。

若涉及设计模式选择、第三方库引入、协议选择等重大决策，必须按 `architecture_decision_record.md` 创建 ADR。

---

# Step 4：文档更新计划

编码前先确定需要同步更新的文档（按 `documentation_rules.md` 判定）。

输出格式：

```markdown
## 文档更新计划

### 必须更新
- docs/architecture.md — [原因]
- docs/api.md — [原因]

### 无需更新
- docs/database.md — [不涉及数据库变更]
```

必须在编码前列出，编码后再次确认。

---

# Step 5：编码实现

遵循 `engineering_rules.md` 的通用原则和 `cpp_project_rules.md` 的 C++ 细节。

同时按 `testing_rules.md` 编写测试代码，按 `task_management_rules.md` 更新任务进度。

关键要求：

* 函数不超过 50 行
* 每个类单一职责
* 所有公共接口有 Doxygen 注释
* 错误路径必须处理
* 新增逻辑必须可测试

禁止：

* 直接输出 500+ 行代码不做任何解释
* 跳过错误处理
* 留下 TODO 注释不跟进

---

# Step 6：自检

编码完成后必须逐项自检。

输出格式：

```markdown
## 自检

✓ SOLID 原则
✓ 命名规范
✓ 注释完整（Doxygen）
✓ 错误处理完整
✓ 线程安全
✓ 异常安全（noexcept 正确标记）
✓ 资源管理（RAII / 智能指针）
✓ 性能（热路径无动态分配）
✓ 魔数已提取为常量
✓ 枚举使用 enum class
```

发现问题必须立即修复，不得标记后忽略。

---

# Step 7：最终确认

全流程最终输出格式：

```markdown
## 完成确认

### 代码变更
- [文件列表]

### 文档同步
- [已更新文档列表]
- [不需要更新及原因]

### 任务状态
- 更新 `docs/tasks/TASK-XXX.md` 进度

### 建议 Commit（不自动执行）
- 格式见 `git_rules.md`

### 变更日志
- [日期] [版本] [简述变更内容] [影响范围]
```

---

# 禁止行为汇总

禁止：

* 跳过需求分析直接编码
* 不做影响分析就修改公共接口
* 只给一种方案不做比较
* 代码变更后文档不同步
* 留下 TODO / FIXME 不跟踪
* 自检发现问题却不修复
* 一次输出超过 300 行代码不做解释
* 忽略用户上下文切换（每次对话必须重新理解项目状态）

---

# 跨对话一致性

每次新对话必须：

1. 回顾 `rules/` 下所有规范文件（按 `engineering_rules.md` 中的加载顺序）
2. 读取 `docs/architecture.md` 了解系统全貌
3. 读取 `docs/tasks/ACTIVE.md` 了解当前任务
4. 确认项目目录结构
5. 确认当前分支和最近的 changelog

禁止在未了解项目上下文的情况下直接编码。
