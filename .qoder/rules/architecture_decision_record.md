# ADR 必须记录的场景

以下情况必须创建 ADR：

* 引入新的设计模式（如 Command、Observer、Strategy）
* 选择第三方库（如 FFmpeg vs GStreamer）
* 架构分层变更（如引入中间件层）
* 通信协议选择（如 Modbus vs CANopen）
* 数据存储方案（如 SQLite vs 文件系统）
* 跨平台兼容性决策（如 Windows only vs 跨平台）
* 性能关键路径的优化策略
* API / ABI 兼容性取舍

# ADR 模板

每个 ADR 文件命名：`ADR-<三位编号>-<简短描述>.md`

```markdown
# ADR-001：使用命令模式实现时间轴撤销/重做

## 背景

项目需要实现时间轴编辑功能，用户需要：

* 撤销（Undo）上一步操作
* 重做（Redo）已撤销的操作
* 支持多种操作类型（移动、删除、属性修改）

## 问题

如何设计才能支持灵活的撤销/重做，同时保持代码可扩展？

## 备选方案

### 方案 A：状态快照模式

每步操作前保存完整状态快照。

- 优点：实现简单
- 缺点：内存占用大（每帧保存完整状态导致内存爆炸），不适合长时间编辑

### 方案 B：命令模式（Command Pattern）

每步操作封装为 Command 对象，维护 execute/undo 接口。

- 优点：内存高效（只存储操作差异），易于扩展新操作类型
- 缺点：每种操作需实现 execute + undo 两个方法，开发量稍大

## 最终方案

**方案 B：命令模式**

## 选择原因

1. 时间轴可能包含数百步操作，快照模式内存不可接受
2. 命令模式天然支持操作队列，与时间轴数据结构一致
3. 新增操作类型只需新增 Command 子类，符合 OCP 原则

## 影响范围

* 新增 `commands/` 模块目录
* 核心模块：`Command.h`（抽象基类）、`CommandQueue.h`（撤销栈/重做栈）
* 所有用户操作需封装为 Command 子类

## 状态

已采纳（2025-06-02）
```

```markdown
# ADR-007：运动控制通信协议选择

## 背景

上位机需要与运动控制卡通信，下发运动指令并接收状态反馈。

主要要求：
- 实时性（指令延迟 < 10ms）
- 可靠性（丢包重传）
- 多轴同步控制

## 问题

选择哪种通信协议？

## 备选方案

### 方案 A：Modbus TCP

- 优点：工业标准，大量设备支持，调试工具丰富
- 缺点：轮询模式实时性差，不支持推送，帧格式固定不灵活

### 方案 B：自定义二进制协议（基于 TCP）

- 优点：极致性能，帧格式完全可控，支持推送
- 缺点：需要自行实现全部协议栈，调试工具从零开始

### 方案 C：EtherCAT

- 优点：微秒级实时性，支持分布式时钟同步
- 缺点：需要专用主站硬件，成本高，开发复杂

## 最终方案

**方案 B：自定义二进制协议**

## 选择原因

1. Modbus TCP 轮询模式无法满足多轴同步控制的实时需求
2. EtherCAT 成本过高，适合高端场景但不符合当前项目定位
3. 自定义协议可以针对本项目精确定制（固定帧头、校验、ACK 机制）

## 影响范围

* 新增 `network/protocols/` 目录
* 核心文件：`MotionFrame.h`、`MotionSerializer.h`、`MotionDeserializer.h`
* 需要配套实现协议测试工具

## 状态

已采纳（2025-07-01）
```

# ADR 管理规则

## 不可修改原则

已采纳的 ADR 不得事后修改内容。

若决策发生变化：

1. 创建新的 ADR 记录新决策
2. 旧 ADR 状态标记为「已替代（见 ADR-XXX）」
3. 更新 `docs/adr/README.md` 索引

禁止：

* 直接修改旧 ADR 内容
* 删除旧 ADR（应保留历史）

## AI 触发规则

AI 在 Step 3（设计方案）时若判断本次变更涉及 ADR 场景，必须：

1. 提醒用户「建议创建 ADR 记录本次决策」
2. 若用户同意，按照模板创建 ADR 文件
3. 更新 README.md 索引
