# AI Coding Rules

## 本文件定位

本文件为规则体系的**根规则文件**。

所有 AI Agent 必须同时加载以下 9 份规范：

```
规则加载顺序（按优先级从低到高）：

1. engineering_rules.md              ← 本文件：软件工程总纲
2. documentation_rules.md            ← 文档编写与同步
3. project_structure_rules.md        ← 项目目录结构
4. task_management_rules.md          ← 任务管理
5. testing_rules.md                  ← 测试体系
6. architecture_decision_record.md   ← 架构决策记录
7. ai_workflow_rules.md              ← AI 工作流
8. cpp_project_rules.md              ← C++ 语言与工程
9. git_rules.md                      ← Git 提交流程
```

---

## 规则冲突优先级

当不同规则文件之间存在冲突时，遵循以下优先级：

```
最高优先级：项目专属规则
     ↑  （如 motion_control_project_rules.md）
     ↑
优先级 3：语言规则
     ↑  （如 cpp_project_rules.md）
     ↑
优先级 2：工作流规则
     ↑  （如 ai_workflow_rules.md、git_rules.md）
     ↑
最低优先级：工程总则
     ↑  （即本文件 engineering_rules.md）
```

**简单记忆**：越接近具体项目，优先级越高。

## 核心职责

你的职责不仅是生成可运行代码。

更重要的是：

* 可读性
* 可维护性
* 可扩展性
* 可测试性
* 可演进性

代码质量优先于开发速度。

---

# 开发流程

任何需求必须遵循：

1. 需求分析
2. 职责分析
3. 模块划分
4. 接口设计
5. 数据模型设计
6. 实现代码

禁止直接输出大量代码。

---

# 架构优先

编码前必须思考：

* 模块边界
* 模块职责
* 依赖关系
* 扩展点

禁止边写边设计。

---

# SOLID

必须遵循：

SRP

OCP

LSP

ISP

DIP

---

# 高内聚

相关逻辑必须放在同一模块。

禁止：

业务逻辑到处散落。

---

# 低耦合

模块之间：

优先：

* 接口
* 依赖注入
* 事件机制
* 消息机制

避免硬依赖。

---

# 命名规范

命名必须表达真实含义。

禁止：

tmp

data

obj

helper

manager

util

推荐：

MotorController

TaskScheduler

UserRepository

NetworkClient

---

# 类设计规范

一个类只负责一个职责。

禁止：

God Object

禁止：

SystemManager管理所有功能。

---

# 函数规范

函数：

* 单一职责
* 输入明确
* 输出明确

建议：

函数长度不超过50行。

复杂逻辑必须拆分。

---

# 设计模式规范

根据问题选择模式：

* Factory
* Strategy
* Observer
* Command
* State
* Adapter
* Decorator

必须说明：

为什么使用。

---

# 线程规范

线程必须：

* 生命周期明确
* 支持退出
* 支持资源释放

禁止：

没有退出条件的无限循环。

必须使用可控退出标志：

```cpp
// 禁止
while (true) { ... }

// 必须
while (running_.load()) { ... }
```

---

> C++ 并发锁实现细节（lock_guard、条件变量等）参阅 `cpp_project_rules.md`

---

# 资源管理规范

优先：

RAII

智能指针

资源自动释放。

禁止：

裸new后无人管理。

---

# 魔数规范

禁止在代码中直接使用字面量。

必须提取为具名常量，命名须表达含义。

> C++ 常量命名约定（k 前缀等）参阅 `cpp_project_rules.md`

---

# 注释规范

注释解释「为什么」，而非「做什么」。

公共接口必须有文档注释（格式因语言而异）。

禁止：

* 注释掉的死代码长期保留（应直接删除）
* 无意义注释，如 `// 加1` 对应 `i++`
* 翻译代码的注释

> C++ Doxygen 注释格式参阅 `cpp_project_rules.md`

---

# 性能规范

热路径（高频调用路径）必须：

* 禁止动态内存分配（`new` / `malloc`）
* 禁止在循环内创建/销毁对象
* 数据结构选择必须说明时间复杂度理由
* 优先使用对象池、内存池复用资源

播放器关键路径（解码、渲染）必须：

* 评估帧率影响
* 避免不必要的数据拷贝（优先移动语义 / 零拷贝）

---

# 安全规范

外部输入必须视为不可信：

* 文件路径、网络数据、用户输入均需校验
* 禁止信任外部传入的长度或偏移量
* 整数运算注意溢出

> C++ 安全规范（禁止不安全 C 函数、边界检查等）参阅 `cpp_project_rules.md`

---

> C++ 编译规范（零警告、头文件保护、包含顺序等）参阅 `cpp_project_rules.md`

---

# 错误处理规范

禁止：

忽略错误

空catch

静默失败

必须：

记录错误

返回错误信息

支持问题追踪。

---

# 日志规范

记录：

* 启动
* 停止
* 异常
* 通信失败
* 状态变化

日志必须帮助定位问题。

---

# 测试规范

新增业务逻辑：

必须可测试。

业务层不得依赖：

* UI
* 数据库
* 网络

方便单元测试。

> 测试框架、覆盖率、四类必测场景（单元/集成/压力/异常）、用例命名等完整规范
> 请参阅 `testing_rules.md`

---

# 规则优先级

当规则之间存在冲突时，遵循以下优先级：

**可维护性 > 可扩展性 > 性能 > 开发速度**

例外条款：

* 规则可豁免，但必须在代码注释中说明豁免原因
* 性能关键路径可豁免部分设计模式要求，但必须有基准测试数据支撑
* 遗留代码重构时，优先渐进式改善，不强制一次性满足所有规则

---

# 兼容性原则

修改旧代码前：

分析：

* 调用链
* 影响范围
* 兼容性

优先扩展。

避免重写。

---

# AI输出要求

输出代码前必须给出：

1. 架构设计
2. 模块职责
3. 类职责
4. 设计模式说明
5. 风险分析

然后再生成代码。

---

# 最终检查

提交前确认：

✓ SOLID

✓ 高内聚

✓ 低耦合

✓ 无God Object

✓ 可测试

✓ 可扩展

✓ 易维护

✓ 命名规范

✓ 错误处理完整

✓ 日志完整

不满足必须重新设计。
